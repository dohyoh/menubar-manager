# 플랫폼 노트 — macOS 27 메뉴바

- 최종 수정: 2026-11-11 (7절 추가: macOS 26.5.2에서 확인한 것 — 숨김 기능 없음, 구분자 확장 방식 동작, 접근성으로 읽기·드래그 합성 동작, 실제 앱에서 숨김 확인)
- 조사 환경: macOS 27.2.1 (26B131), Apple silicon, 디스플레이 2대(내장 + 외부). Xcode 26.6 / Swift 6.3.3 → 작업 중 Xcode 27.2 / Swift 6.4.2로 업데이트됨
- 관련: [ADR-0003](../adr/0003-visibility-mechanism.md) · [ADR-0004](../adr/0004-reorder-mechanism.md) · [ADR-0010](../adr/0010-install-location.md) · [Spikes/](../../Spikes/README.md)

이 문서는 "macOS 메뉴바가 실제로 어떻게 동작하는가"에 대한 사실 기록입니다. 설계 결정은 ADR에 있습니다. 1~6절은 macOS 27, [7절](#7-macos-26에서-확인한-것-)은 macOS 26에 대한 내용입니다.

**표기:** ✅ `검증됨` 이 Mac에서 직접 확인 · 📰 `보고됨` 외부 출처, 직접 확인 전 · ❓ `미확인` 가설

## 1. 요약

- macOS 27은 **메뉴바 전체를 `MenuBarAgent` 프로세스의 창 하나로 그립니다.** 아이템별 창이 없어 기존 관리 앱의 기법은 통하지 않습니다. ✅
- 비공개 **허용 목록 기능(`MBAssessmentModeAssertion`)으로 앱 단위 숨김이 됩니다.** 일반 앱에서 특별한 권한 없이 켜지고, 해제·강제 종료 시 자동 복구됩니다. ✅
- **앱이 `/Applications`에 있어야** 그 앱의 아이콘이 허용 목록과 매칭됩니다. 다른 위치의 앱은 허용해도 숨겨집니다. ✅
- 제어 센터에서 메뉴바로 꺼낸 모듈(타이머 등)은 제한 중 항상 숨겨집니다. ✅
- 아이콘 좌클릭/우클릭은 구분되어 전달됩니다. ✅
- 접근성 권한이 있으면 **메뉴바 아이템의 위치를 읽고, ⌘+드래그를 합성해 순서를 바꿀 수 있습니다.** ✅ (3.21~3.23)

## 3. 이 Mac에서 직접 확인한 것 ✅

2026-11-10. 검증 코드는 [Spikes/MenuBarSpike](../../Spikes/MenuBarSpike/)에 있습니다. 확인 방법은 "적용 → 메뉴바 영역 화면 캡처 → 비교"와 `MenuBarAgent` 통합 로그 조회입니다.

### 3.1 창 구조

| 소유 프로세스 | 레이어 | 크기 | 비고 |
|---|---|---|---|
| `MenuBarAgent` | 24 | 1728×33 | 내장 디스플레이 메뉴바 |
| `MenuBarAgent` | 24 | 2560×30 | 외부 디스플레이 메뉴바 |
| `Window Server` | 24 | 위와 같음 | 메뉴바 배경 |

- 아이템별 창이 **없습니다.** 다른 앱의 아이템 크기·위치는 창 목록(`CGWindowListCopyWindowInfo`)으로 알 수 없습니다.
- 관련 프로세스: `MenuBarAgent`, `ControlCenter`, `SystemUIServer`.

### 3.2 비공개 프레임워크

`/System/Library/PrivateFrameworks/MenuBarClientCore.framework` (런타임 조회로 확인):

```
MBAssessmentModeConfiguration
  - initWithAllowedSystemItems:(NSArray<NSNumber*>*) allowedBundleIdentifiers:(NSArray<NSString*>*)
  - initWithUnrestrictedMenuBarItems

MBAssessmentModeAssertion
  - activateWithConfiguration:completionHandler:     // 핸들러: void (^)(NSError *)
  - invalidate
```

같은 이미지의 다른 클래스: `MBMenuBarItemManager`, `VisibilityRestrictionAssertion`, `TrackedApplicationsPreferences` 등. `MenuBarClient.framework`에는 `MBEditModeAssertion`, `MBControlCenterDragAssertion` 등이 있습니다 (용도 미확인).

### 3.3 허용 목록으로 숨기기 — S1

- `dlopen` + `NSClassFromString`으로 접근해 `activateWithConfiguration:completionHandler:`를 호출하면 **허용 목록에 없는 앱의 아이콘이 사라집니다.** 완료 핸들러의 오류는 nil.
- **특별한 권한이 필요 없습니다.** entitlement 없이, 번들 ID가 없는 명령줄 도구에서도, 임시(ad-hoc) 서명 앱에서도 동작했습니다.
- 사라진 자리는 남은 아이콘이 메웁니다. 적용·해제는 1초 안에 반영됩니다.
- `MenuBarAgent` 로그: `[com.apple.menubar:visibilityRestriction] didActivateVisibilityRestriction` / `didInvalidateVisibilityRestriction`.

### 3.4 복구 — S2

| 상황 | 결과 |
|---|---|
| `invalidate` 호출 | 즉시 전부 복구 |
| 앱 정상 종료 | 복구 |
| `SIGKILL`로 강제 종료 (해제 없이) | 2초 안에 전부 복구 |

시스템이 연결 종료를 감지해 제한을 풉니다(`VisibilityRestrictionServer received invalidation`). **별도 감시 프로세스가 필요 없습니다.**

### 3.5 시스템 아이템 번호 — S4

`allowedSystemItems`에 넣은 번호의 시스템 아이템만 남습니다. 빈 배열이면 시스템 아이템도 전부 숨겨집니다.

| 번호 | 아이템 |
|---|---|
| 0 | 배터리 |
| 2 | 시계 |
| 6 | Wi-Fi |
| 8 | 제어 센터 |

- 이 Mac의 메뉴바에 보이던 4개만 확인했습니다. 다른 번호(Bluetooth, 사운드, Spotlight 등)는 미확인입니다.
- 실제 앱에서 Wi-Fi(6)만 빼고 숨김을 걸어 Wi-Fi 아이콘만 사라지고, 다시 넣으면 돌아오는 것을 확인했습니다 (2026-11-10). 앱이 숨길 수 있게 내놓는 것은 확인된 Wi-Fi·배터리뿐이고, 시계·제어 센터는 항상 허용합니다.
- 128 이상 번호에는 이 Mac에서 대응하는 아이템이 없었습니다.
- 기본값은 `0...255` 전체 허용이 안전합니다.

### 3.6 제한 중 항상 숨겨지는 것

- **제어 센터에서 메뉴바로 꺼낸 모듈**(이 Mac에서는 타이머 `⏱0:00`)은 시스템 아이템 번호를 `0...4095`까지 허용해도 제한 중에는 숨겨졌습니다. 해제하면 돌아옵니다.
- **`/Applications` 밖에서 실행된 앱의 아이콘** (3.7).

### 3.7 `/Applications` 요건 ⚠️

**앱이 `/Applications`에 있어야 `MenuBarAgent`가 그 앱의 아이콘을 번들 ID와 연결합니다.**

| 실행 위치 | `MenuBarAgent` 로그 | 허용 목록에 넣었을 때 |
|---|---|---|
| 프로젝트 빌드 폴더 | `hosting client 0[pid-nil]` | 숨겨짐 ❌ |
| `~/Applications` | `hosting client 0[pid-nil]` | 숨겨짐 ❌ |
| `/Applications` | `hosting client 0[pid-dev.…spike2]` | 표시됨 ✅ |

- NSStatusItem(Objective-C)과 SwiftUI `MenuBarExtra` 모두 같은 결과였습니다. Info.plist 구성, 아이콘 방식, 서명 종류와는 무관했습니다.
- LaunchServices 레코드는 위치와 무관하게 정상이었습니다. 원인은 `MenuBarAgent` 내부 규칙으로 보이며 문서화되어 있지 않습니다.
- **영향 ①** 이 앱은 반드시 `/Applications`에 설치되어야 자기 아이콘을 유지합니다. 개발 중에도 빌드 후 `/Applications`로 복사해 실행해야 합니다. → [ADR-0010](../adr/0010-install-location.md)
- **영향 ②** 사용자의 다른 앱 중 `/Applications` 밖에 있는 것(개발 중인 앱, `~/Applications`의 앱)은 **숨김 적용 중에는 표시할 수 없습니다.**
- 미확인: `/Applications`의 하위 폴더, `/System/Applications`, 다른 앱 번들 안에 든 헬퍼 앱.

### 3.8 허용 목록 교체

- 같은 `MBAssessmentModeAssertion` 객체로 `activate…`를 다시 호출하면 **이전 제한이 해제되지 않고 누적됩니다.** `invalidate`는 마지막 것만 해제해 일부가 남습니다.
- **올바른 교체:** 새 객체를 만들어 활성화 → 완료 핸들러에서 이전 객체를 `invalidate`. 깜빡임 없이 목록이 바뀝니다.
- 제한이 동시에 여러 개 켜져 있을 때의 합성 규칙은 미확인입니다. **항상 1개만 유지**하도록 구현합니다.

### 3.9 그 밖에 확인한 것

- **자기 아이콘의 위치:** 자기 `NSStatusItem`의 `button.window.frame`은 실제 화면 위치를 돌려줍니다 (예: `{1177, 1081, 28, 39}`).
- **새 앱 추적:** 새 앱이 아이콘을 만들면 `MenuBarAgent`가 자동으로 추적 목록에 넣습니다 (`Started to track application .bundle(…)`). 기본값은 표시 허용.
- **위치 저장:** `MenuBarAgent`가 아이템 위치를 직접 저장합니다 (`Persisting trailing item positions`).
- **추적 목록 저장소:** `~/Library/Group Containers/com.apple.MenuBar`. 보호되어 있어 읽을 수 없습니다 (S8 불가). `com.apple.controlcenter` 설정에는 시스템 아이템의 `NSStatusItem Visible…` 키만 있습니다.
- **최소 OS 지정 주의:** `swiftc`의 기본 대상 버전이 실행 중인 OS보다 높게 잡혀 실행이 거부될 수 있습니다(오류 -10825). 빌드 시 대상 버전을 명시합니다.
- **서명:** 키체인이 서명 키 접근을 물으면 `codesign`이 사용자 입력을 기다리며 멈춥니다. 자동화에서는 "항상 허용"을 한 번 해 두거나 임시 서명을 씁니다.

### 3.10 좌클릭/우클릭

검증용 앱의 아이콘을 사용자가 직접 클릭한 기록(2026-11-10 14:48)으로 확인했습니다.

- `button.sendAction(on: [.leftMouseUp, .rightMouseUp])` + `NSApp.currentEvent.type`으로 좌클릭(`leftMouseUp`)과 우클릭(`rightMouseUp`)이 구분되어 전달됩니다.
- 좌클릭 6회 → 숨김 적용/해제가 번갈아 실행됨. 우클릭 1회 → 메뉴가 열리고 닫힘.
- 단일 창 구조(`MenuBarAgent`가 그리는 메뉴바)에서도 서드파티 상태 아이템의 클릭은 정상 전달됩니다.
- **메뉴 안의 스위치:** `NSMenuItem.view`에 글자 + `NSSwitch`를 넣은 항목이 정상 표시되고, 메뉴가 열린 채로 스위치를 조작할 수 있습니다. 스위치를 켜 숨김이 적용되자 약 1초 뒤 메뉴가 닫혔습니다 (1회 관찰, 숨김 적용으로 메뉴바가 다시 배치되기 때문으로 추정).

### 3.11 설정 창 (메뉴바 관리)

검증용 앱에 최소 구현을 넣어 확인했습니다 (`Spikes/MenuBarSpike/SettingsWindow.m`).

- 메뉴바 전용(`LSUIElement`) 앱은 창을 열 때 **앱을 직접 활성화**해야 창이 앞에 보입니다 (`NSApp.activate` + `makeKeyAndOrderFront`).
- 숨김 적용 중에 설정 창에서 앱의 스위치를 끄면 그 앱의 아이콘이 즉시 사라지고, 켜면 돌아옵니다 (허용 목록 교체, 깜빡임 없음).
- 앱 목록은 권한 없이 "실행 중인 앱 + `/Applications`에 설치된 앱"으로 만들 수 있습니다. 이 Mac에서 38개.
- **한계:** 접근성 권한 없이는 "메뉴바 아이콘을 실제로 가진 앱"만 골라낼 수 없어, 실행 중 목록에 아이콘이 없는 일반 앱(Finder, 브라우저 등)도 함께 나옵니다. S5가 통과하면 걸러낼 수 있습니다.
- `/Applications` 밖에서 실행 중인 앱은 목록에서 "숨김 중에는 표시할 수 없음"으로 구분해 보여 줄 수 있습니다 (이 Mac에서 2개 해당).

### 3.12 수동 ⌘+드래그

- ⌘(Command)를 누른 채 메뉴바 아이콘을 드래그하면 **순서가 바뀝니다.** 사용자가 이 Mac에서 직접 해 보고 확인했습니다 (2026-11-10).
- 따라서 "정보" 화면이 안내하는 방법은 유효합니다.
- 확인된 것은 **사람이 직접 하는 드래그**입니다. 프로그램이 같은 동작을 합성해도 되는지(S6)는 별개이며 아직 미확인입니다.

### 3.13 자기 아이콘이 숨겨졌는지는 알 수 없다

- 허용 목록에서 자기 자신을 빼고 숨김을 켜 자기 아이콘을 일부러 숨긴 뒤, 자기 `NSStatusItem`의 값을 읽어 봤습니다. `button.window.frame`, `window.isVisible`, `window.occlusionState`, `statusItem.isVisible` **모두 숨기기 전과 같았습니다.**
- 따라서 "숨김 직후 자기 아이콘이 보이는지 확인"하는 안전장치는 만들 수 없습니다. 원인(설치 위치)을 미리 막는 방식으로 대체합니다. → [ADR-0010](../adr/0010-install-location.md)

### 3.14 실제 앱(MenuBarManager)에서 확인한 것

검증용 앱이 아니라 제품 코드(`/Applications/MenuBarManager.app`, Debug 빌드)로 확인한 내용입니다.

- 숨기기 켬 → 지정한 앱 아이콘이 사라지고 자기 아이콘은 남음. 좌클릭 경로(토글) → 전부 표시. 자동 다시 숨기기(3초로 설정) → 시간이 지나 다시 숨김.
- 우클릭 메뉴(숨기기 스위치 · 설정… · 정보 · 종료)가 숨김 상태와 꺼진 상태 모두에서 정상 표시.
- 설정 창(메뉴바 관리 / 일반), 정보 창 표시. 설정은 재실행 후 복원.
- SwiftUI `TabView`를 창에 그대로 넣으면 탭 전환 컨트롤이 제목 표시줄에 가려졌습니다. 탭 전환을 내용 영역 안의 분할 컨트롤로 바꿔 해결했습니다.
- 위 확인은 명령 채널(Debug 전용)로 같은 코드 경로를 실행하고 화면을 캡처한 것입니다. **마우스로 직접 누르는 확인은 사용자 몫으로 남아 있습니다.**

### 3.15 개발 환경에서 겪은 것

- Xcode가 자동 업데이트되면 라이선스 동의 전까지 `swift build`가 실패합니다 (`sudo xcodebuild -license`).
- Xcode 업데이트 직후 `xcodebuild`가 CoreSimulator·CoreDevice 관련 경고를 많이 출력하지만 macOS 앱 빌드에는 영향이 없었습니다.

### 3.16 메뉴 안의 스위치는 직접 그려야 한다

- 시스템 `NSSwitch`를 메뉴 항목에 넣으면 **켜진 상태가 강조색(파란색)이 아니라 회색으로** 그려집니다. 스위치는 자기 창이 활성 창일 때만 강조색을 쓰는데, 메뉴바 전용 앱의 메뉴는 활성 창이 아니기 때문입니다. 사용자가 "켜져도 꺼진 것처럼 보인다"고 보고해 확인했습니다.
- 해결: 켜짐을 항상 강조색으로 그리는 스위치를 직접 그립니다 (`MenuBarUI/MenuSwitch.swift`). 설정 창 안의 스위치는 창이 활성화되므로 시스템 스위치를 그대로 씁니다.
- 스위치를 눌러도 메뉴는 닫히지 않고, 메뉴가 열린 채로 아이콘과 메뉴바가 즉시 바뀝니다 (실제 앱에서 화면 캡처로 확인).

### 3.17 검증할 때 주의할 점

- `screencapture -R`(영역 지정)로 찍으면 열려 있는 메뉴가 **찍히지 않았습니다.** 전체 화면으로 찍은 뒤 잘라야 합니다.
- 메뉴를 여는 코드를 Swift `Task` 안에서 실행하면, 메뉴가 닫힐 때까지 다른 메인 액터 작업이 밀립니다 (스위치를 눌러도 상태가 메뉴를 닫은 뒤에야 바뀜). 실제 클릭은 `Task` 밖에서 일어나므로 이 문제가 없습니다. 자동 검증도 `Task` 밖에서 메뉴를 열도록 했습니다.

### 3.18 지역화

- Swift 패키지의 문자열 카탈로그(`Localizable.xcstrings`)에 한국어 원문 + 영어 번역을 두면, 빌드 결과물에는 `en.lproj`만 생깁니다 (원문 언어는 키가 곧 문자열).
- **앱의 Info.plist에 `CFBundleLocalizations`(ko, en)를 선언하지 않으면 영어 환경에서도 한국어로만 나옵니다.** 앱 번들이 영어를 지원한다고 알려 줘야 패키지의 영어 번역이 쓰입니다. 영어(`-AppleLanguages "(en)"`)와 한국어 실행 모두 캡처로 확인했습니다.

### 3.19 로그인 항목

- 설정의 "로그인 시 실행"을 사용자가 켠 뒤 `SMAppService.mainApp.status`가 `enabled`로 읽히는 것을 확인했습니다 (임시 서명 빌드에서도 등록됨).
- **재부팅 후 자동 실행을 확인했습니다** (2026-11-10 17:58 재시작 → 17:59 앱 자동 실행). 실행되자마자 저장된 설정대로 숨김이 다시 적용됐고, 자기 아이콘은 보였으며, 접근성 권한도 유지됐습니다.
- 재부팅 전후로 메뉴바 아이콘 순서가 같았습니다 (모니터 오른쪽 끝 기준 거리로 비교: 574, 455, 419, 379, 322, 283, 245, 203, 164). 시스템이 순서를 기억합니다.

### 3.20 접근성 권한 항목은 서명에 묶인다

- 시스템은 접근성 권한을 줄 때 그 시점 앱의 서명 조건을 함께 저장합니다. 이후 서명이 달라지면 목록에 켜져 있어도 거부됩니다. 시스템 로그에는 `Failed to match existing code requirement for subject dev.menubarmanager.app and service kTCCServiceAccessibility`로 남습니다.
- 실제로 겪은 일: 임시 서명 빌드일 때 만들어진 권한 항목이 남아 있어, 고정 인증서로 서명한 빌드에서는 "허용 안 됨"으로 읽혔습니다. 앱을 다시 실행해도 같았습니다.
- 해결: 기존 항목을 지우고 다시 허용합니다 — `tccutil reset Accessibility dev.menubarmanager.app` 실행 후 시스템 설정에서 다시 켜기. 그 뒤로는 고정 인증서 서명이 유지되는 한 재빌드해도 권한이 유지됩니다.
- 검증용 앱(MenuBarSpike)도 같은 이유로 거부됩니다 (권한 항목은 개발 인증서 서명 기준인데 지금 빌드는 임시 서명).

### 3.21 접근성으로 메뉴바 아이템 읽기 — S5

- 각 앱의 접근성 요소 `AXExtrasMenuBar`의 자식에서 아이템의 위치·크기를 읽을 수 있습니다. 서드파티 앱은 자기 프로세스에, 시스템 아이템(시계, Wi-Fi 등)은 `MenuBarAgent` 프로세스에 있습니다.
- **숨겨졌거나 표시되지 않는 아이템도 예전 좌표를 돌려줍니다.** 숨김 중에 읽으면 숨긴 앱의 좌표가 보이는 아이템과 겹쳐 나옵니다. "메뉴 막대에서 허용"이 꺼진 앱도 마찬가지입니다.
- **가려내는 방법:** 아이템의 중심 좌표에 실제로 무엇이 있는지 확인합니다 (`AXUIElementCopyElementAtPosition`). 그 자리의 요소가 같은 프로세스의 `AXMenuBarItem`이면 표시된 것이고, 아니면(다른 앱의 메뉴바, 없음) 예전 좌표입니다. 이 방식으로 표시된 아이템만 정확히 남았습니다.
- 따라서 숨긴 앱까지 포함한 실제 순서는 **전부 펼친 상태에서** 읽어야 합니다.
- 시스템 아이템은 제목·설명·식별자가 모두 비어 있어 이름을 알 수 없습니다. 식별자가 "앱 안에서의 순번"이라, 시스템 아이템이 생기거나 사라지면(AirPods 연결 등) 번호가 바뀝니다. 순서는 매번 새로 읽어야 합니다.
- 실행 중인 모든 앱(약 85개)을 훑으면 2~3초 걸립니다. 응답이 느린 앱이 가끔 빠질 수 있어 앱별 대기 시간을 0.4초로 두었고, 한 번 훑은 뒤에는 아이템이 있던 프로세스만 다시 봅니다. 조회는 메인 스레드 밖에서 실행합니다.

### 3.22 ⌘+드래그 합성으로 순서 바꾸기 — S6·S7

- `CGEvent`로 "⌘을 누른 채 마우스 누름 → 이동 → 놓음"을 합성하면 **실제로 아이콘 순서가 바뀝니다.** 숨긴 앱도 펼친 상태에서 같은 방법으로 옮겨집니다.
- **속도가 중요합니다.** 12걸음·30ms 간격으로 빠르게 끌었을 때는 목표까지 가지 못하고 한 칸만 이동했습니다. 6pt마다 한 걸음·12ms 간격으로 끌고 놓기 전에 250ms 멈추니 목표 위치에 정확히 들어갔습니다.
- **놓는 지점:** 목표 아이템의 왼쪽 가장자리에서 6pt 왼쪽에 놓으면 그 아이템 바로 앞에 들어갑니다 (왼쪽·오른쪽 이동 모두 확인).
- 서드파티 아이콘을 시스템 아이템 사이(타이머와 Wi-Fi 사이)로 옮길 수 있습니다. 시스템 아이템 자체를 옮기는 것은 시험하지 않았고, 구현에서도 옮기지 않습니다.
- 실제 앱의 전체 흐름(숨김 풀기 → 읽기 → 드래그 → 다시 읽어 확인 → 다시 숨김)으로 Magnet을 옮겼다가 원래 자리로 되돌리는 것을 확인했습니다.
- 드래그하는 동안 포인터가 실제로 움직이고, 끝나면 원래 자리로 돌려놓습니다. 사용자가 다른 작업을 하는 중이면 방해가 됩니다.
- 미확인: 폭이 넓은 아이콘(텍스트가 있는 아이템)을 옮길 때의 정확도, 시스템 아이템 이동.

### 3.23 모니터가 여러 대일 때

- 메뉴바는 모니터마다 하나씩 있고 같은 아이템을 보여 주지만, 접근성 API는 아이템마다 **하나의 좌표만** 돌려줍니다. 그 좌표가 어느 모니터 기준인지는 아이템마다 다를 수 있습니다 (활성 모니터가 바뀐 직후 일부는 외부 모니터, 일부는 내장 모니터 좌표로 읽힘).
- x 좌표로 정렬하면 순서가 뒤섞입니다. 실제로 겪었습니다.
- **해결:** "아이템이 놓인 모니터의 오른쪽 끝에서 아이템 왼쪽 가장자리까지의 거리"로 비교합니다. 메뉴바 아이템은 오른쪽 정렬이라 이 거리는 어느 모니터 기준이든 같았습니다 (예: 사용량 위젯은 두 모니터 모두 574). 드래그 목적지도 옮길 아이템이 놓인 모니터 기준으로 환산합니다.
- 전제: 두 모니터의 메뉴바 배치가 같아야 합니다. 한쪽 모니터가 좁아 일부 아이템이 넘침 화살표 뒤로 접힌 경우는 다루지 못합니다.

### 3.24 숨김 중에는 알림 센터가 열리지 않는다 — S3

- **현상(검증됨):** 숨김이 걸려 있는 동안에는 시계를 눌러도 알림 센터가 열리지 않습니다. 알림 배너는 정상으로 뜹니다. 숨김을 풀면 바로 열립니다. 외부 보고(BTT 커뮤니티)와 같습니다.
- **원인:** 알림 센터 프로세스(`com.apple.notificationcenterui`)가 메뉴바 표시 제한을 감시하다가(`visibilityRestrictionMonitor`), 제한 중이면 패널을 열지 않습니다. 이 제한은 원래 시험 감독 모드용이라 의도된 동작입니다.
- **해결:** 시계 영역에서 마우스 누름을 감지하면(전역 마우스 모니터) 그 순간 숨김을 풉니다.
  - 누르고 떼기까지가 약 **0.12초 이상**이면 같은 클릭으로 알림 센터가 열립니다. **0.06초**처럼 아주 빠른 클릭은 숨김이 풀리기 전에 끝나 열리지 않습니다.
  - 그래서 접근성 권한이 있고 시계 위치를 정확히 아는 경우에는, 버튼을 뗀 뒤 0.3초 후에도 알림 센터가 열리지 않았으면 같은 자리를 한 번 더 눌러 줍니다. 실제 앱에서 빠른 클릭으로도 열리는 것을 확인했습니다.
  - 알림 센터가 열려 있는 동안 다시 숨기면 **알림 센터가 닫힙니다.** 그래서 열려 있는 동안에는 다시 숨기기를 미루고, 닫히면 곧바로 다시 숨깁니다 (0.15초마다 열림 여부를 확인). 실제 앱에서 잰 값: 닫는 클릭을 뗀 뒤 **약 0.3~0.4초**에 숨김으로 돌아감 (2회). 5초 넘게 열어 두어도 그동안은 숨기지 않았고, 포인터가 메뉴바 밖에 있든 시계 위에 있든 같았습니다. 다시 숨기면 알림 센터 프로세스의 남은 창도 함께 사라졌습니다.
- **숨김을 유지한 채로는 열 수 없습니다 (검증됨, 2026-11-11):** 프레임워크가 내보내는 기호를 보면, 알림 센터가 받는 값(`MBVisibilityRestrictionState`)은 `active` / `inactive` 둘뿐입니다. 허용 목록의 내용(어떤 앱·시스템 아이템을 허용했는지)은 전달되지 않습니다. 따라서 "아이콘은 숨긴 채 알림 센터만 허용"하는 설정은 존재하지 않고, 알림 센터가 열려 있는 동안에는 숨긴 아이콘이 함께 보일 수밖에 없습니다. 제한의 출처는 `assessmentMode`, `campoDrag`, `userSessionTransition` 세 가지이며 어느 것이든 같은 값으로 전달됩니다.
- **알림 센터가 열려 있는지 판별:** 창 목록만으로는 알림 배너와 구분할 수 없습니다. 접근성 권한이 있으면 알림 센터 프로세스의 접근성 트리에 식별자 `widget-editor-button`("위젯 편집" 버튼)이 있을 때만 열린 것으로 봅니다 (배너만 떠 있을 때는 없음). 권한이 없으면 알림 센터 창이 있는지로 대신합니다.
- **전체 화면에서의 오인 방지:** 전체 화면 앱에서는 메뉴바가 가려져 있어, 오른쪽 위 모서리 클릭이 시계 클릭으로 잘못 잡힐 수 있습니다. 그래서 누른 자리에 실제로 메뉴바가 있는지 먼저 확인합니다 — 접근성 권한이 있으면 그 자리의 요소가 `MenuBarAgent` 프로세스의 것인지, 없으면 `MenuBarAgent`의 창이 그 지점을 덮는지 봅니다. 시계 자리는 참, 화면 한가운데는 거짓으로 판정되는 것을 확인했습니다(권한 있는 경우). 메뉴바 왼쪽의 앱 메뉴 영역은 앞에 있는 앱의 것이라 거짓입니다. 실제 전체 화면 앱에서의 동작은 미확인입니다.
- **닫은 뒤에도 창이 남습니다:** 알림 센터를 닫아도 그 프로세스의 화면 전체 크기 창(레이어 23) 하나가 한동안(3분 이상 관찰) 화면에 남았다가 사라집니다. 창 목록의 값은 열려 있을 때와 같아 구분할 수 없습니다. 따라서 접근성 권한이 없으면 닫은 뒤 다시 숨기기가 그 창이 사라질 때까지 늦어집니다. (데스크탑 위젯도 같은 프로세스의 창이라, 일반 창보다 위에 있는 창만 봅니다 — 위젯이 있는 구성은 미확인.)
- **한계:**
  - 트랙패드 두 손가락 쓸기, 단축키, 핫 코너로 여는 경우는 감지할 수 없어 숨김 중에는 열리지 않습니다. 먼저 좌클릭으로 펼쳐야 합니다.
  - 접근성 권한이 없으면 시계 영역을 오른쪽 끝 170pt로 추정하고, 빠른 클릭은 한 번 더 눌러야 할 수 있습니다.
  - 미확인: 전역 마우스 모니터가 접근성 권한 없이도 메뉴바 클릭을 받는지 (이 Mac은 권한이 있는 상태에서만 확인).
  - 제어 센터는 숨김 중에도 열립니다.

### 3.25 전역 단축키

- Carbon의 `RegisterEventHotKey`로 등록합니다. 접근성·입력 모니터링 권한이 필요 없습니다.
- 실제 앱에서 임시 조합(⌃⌥⇧⌘Y)을 "설정 열기"에 걸고 그 키를 합성해 눌러 설정 창이 열리는 것을 확인했습니다 (2026-11-10).
- 표시 문자는 눌린 글자가 아니라 키 위치(미국식 자판)로 정합니다. 한글 입력 상태에서 기록해도 "ㅛ"가 아니라 "Y"로 보이게 하려는 것입니다. (실제 한글 입력 상태에서의 기록은 미확인)
- **검증할 때 주의:** 합성한 기능 키(F18, F19)는 단축키로 인식되지 않았습니다. 글자 키 조합은 인식됩니다. 실제 키보드의 기능 키가 단축키로 동작하는지는 미확인입니다.
- 다른 앱이 이미 쓰는 조합은 등록이 실패할 수 있고, 그 경우 설정 화면에 표시합니다. (실패 사례는 직접 만들어 보지 못했습니다.)

### 3.26 메뉴바 아이콘을 가진 앱 가려내기

- 실행 중인 앱마다 `AXExtrasMenuBar`에 자식이 있는지 보면 메뉴바 아이콘을 가진 앱을 알 수 있습니다 (접근성 권한 필요). 숨김 중이든 펼친 상태든 결과가 같았습니다 (숨긴 앱도 포함).
- 이 Mac에서는 실행 중인 앱 39개 중 4개만 아이콘을 가졌습니다. 권한이 없을 때의 "실행 중" 목록에는 Safari·Finder처럼 아이콘이 없는 앱이 섞입니다.
- 접근성 정보를 내놓지 않는 앱이 있다면 이 목록에서 빠집니다. 그런 앱은 "실행 중"·"전체" 필터나 검색으로 찾을 수 있습니다.

### 3.27 앱 실행 알림은 Dock에 나오지 않는 앱에는 오지 않는다

- `NSWorkspace.didLaunchApplicationNotification`은 **Dock에 나오지 않는 앱(`LSUIElement`)이 실행될 때는 오지 않습니다.** 시험용 앱을 실행해 확인했습니다 — 알림 0회, `runningApplications` 관찰(KVO)은 3회. 메뉴바 앱은 대부분 이런 앱입니다.
- 처음에는 이 알림에 의존해서, 숨김 중에 새로 설치한 메뉴바 앱을 실행하면 허용 목록이 갱신되지 않아 아이콘이 보이지 않았습니다 (응용 프로그램 폴더에 이미 있던 앱은 목록에 미리 들어가 있어 괜찮았음).
- **해결:** `NSWorkspace.shared.runningApplications`를 관찰하고, 번들 ID 집합이 달라졌을 때만 0.3초 모아서 알립니다. 실제 앱에서 시험용 앱을 실행·종료할 때 앱 목록이 40 → 41 → 40으로 바뀌는 것을 확인했습니다.

### 3.28 서명과 접근성 권한의 보안

- 접근성 권한을 가진 앱은 입력을 합성할 수 있으므로, 다른 프로세스가 이 앱을 통해 그 권한을 빌려 쓰지 못하게 해야 합니다.
- 강화된 런타임 없이 서명하면 환경 변수로 라이브러리를 끼워 넣을 수 있습니다. `build.sh`가 다시 서명할 때 `--options runtime`을 붙이도록 했고, 붙인 뒤에도 숨김·접근성 권한·Debug 빌드의 동적 라이브러리 로딩이 그대로 동작함을 확인했습니다.
- Debug 빌드의 명령 채널(`AutomationHook`)은 같은 사용자의 어떤 프로세스든 실행 인자를 주어 켤 수 있습니다. Release 빌드에는 들어가지 않으므로 평소에는 Release로 설치합니다.

### 3.29 한국어·영어가 아닌 환경의 화면 언어

- 검증됨 (2026-11-11, 실행 인자 `-AppleLanguages`로 언어를 바꿔 설정 창을 확인).
- (1.0.1 기준 — 지금은 3.30처럼 시작할 때 언어를 직접 지정합니다.) 사용자의 선호 언어에 앱이 지원하는 언어(ko, en)가 하나도 없으면, 앱 묶음 `Info.plist`의 `CFBundleDevelopmentRegion`이 화면 언어가 됩니다. 이 값이 `ko`일 때는 중국어·일본어만 설정된 환경에서 화면이 한국어로 나왔고, `en`으로 바꾸자 영어로 나왔습니다.
- 한국어가 선호 언어에 들어 있으면(`ko`, `ko-KR, en-US`, `zh-Hans, ko`) 그대로 한국어로 나옵니다.
- **패키지의 `defaultLocalization`은 `ko`로 둬야 합니다.** `en`으로 바꾸면 문자열 카탈로그(원문 한국어)에서 `ko.lproj`가 만들어지지 않아 한국어 환경에서도 영어로 나옵니다.

### 3.30 앱 안에서 화면 언어 바꾸기

- 검증됨 (2026-11-11, 설정 사본으로 실행한 Debug 빌드의 로그와 설정 창 캡처로 확인).
- 화면 언어는 프로세스가 문자열을 처음 찾을 때 `AppleLanguages` 기본값으로 정해지고, 그 뒤로는 바뀌지 않습니다. 실행 중에 바꾸는 공개된 방법은 없습니다. 그래서 **언어는 앱을 시작할 때 한 번 지정하고, 바꾸려면 다시 시작**합니다.
- 지정하는 방법: `main.swift`의 맨 앞(`NSApplication`을 만들기 전)에서, 실행 인자가 들어가는 자리(`UserDefaults`의 argument domain)에 `AppleLanguages`를 넣습니다. 실행 인자 `-AppleLanguages`를 준 것과 같은 효과이고, 이 자리는 프로세스가 끝나면 사라지므로 **디스크에 기본값 파일을 만들지 않습니다** (`~/Library/Preferences`에 이 앱의 파일이 생기지 않는 것을 확인).
- **설정이 "시스템을 따름"일 때도 항상 지정합니다.** 어떤 언어가 될지를 앱의 판단(`AppLanguage`)과 macOS의 판단이 어긋나지 않게 하려는 것입니다. 이때는 원래 식별자를 앞에 둡니다 (예: `["en-GB", "en"]`).
- 지원 언어: 한국어, 영어, 중국어 간체(`zh-Hans`). 번체(`zh-Hant`, 대만·홍콩·마카오)는 지원하지 않는 언어로 보고 영어로 표시합니다.
- 확인한 조합:

  | macOS 선호 언어 | 설정에서 고른 것 | 화면 | 설정의 표시 |
  |---|---|---|---|
  | 한국어 | (처음 상태) | 한국어 | 한국어 (시스템) |
  | 한국어 | 简体中文 → 다시 시작 | 중국어 | 简体中文 |
  | 한국어 | English → 다시 시작 | 영어 | English |
  | 일본어 | (처음 상태) | 영어 | English (표기 없음) |
  | 중국어 간체 (`zh-Hans-CN`) | (처음 상태) | 중국어 | 简体中文（系统） |
  | 중국어 번체 (`zh-Hant-TW`) | (처음 상태) | 영어 | English (표기 없음) |
  | 영국 영어, 한국어 (`en-GB, ko-KR`) | (처음 상태) | 영어 | English (System) |

- **다시 시작하는 방법:** 새 프로세스를 먼저 띄우고 끝내면 둘이 잠깐 함께 돌아 숨김 제한과 전역 단축키 등록이 겹칩니다. 그래서 이 프로세스가 끝나기를 기다렸다가 `open`으로 다시 여는 작은 도우미(`/bin/sh`)를 띄우고 곧바로 종료합니다. 다시 시작 명령에서 새 프로세스가 숨김을 다시 적용하기까지 약 0.4초였습니다. 실행 인자는 그대로 넘깁니다.
- 미확인: 시스템 설정 > 일반 > 언어 및 지역 > 응용 프로그램에서 이 앱의 언어를 따로 지정한 경우 (그 값이 선호 언어로 읽혀 "(시스템)"으로 표시될 것으로 보이지만 해 보지 않음).

## 7. macOS 26에서 확인한 것 ✅

2026-11-11. 환경: macOS 26.5.2 (25F84), Apple silicon(Mac16,7), 내장 디스플레이 1대(2056×1329pt, 메뉴바 높이 39pt), Xcode 26.0.1 / Swift 6.2. 7.1~7.6은 권한 **없이**, 7.7~7.9는 접근성 권한을 준 검증용 앱으로, 7.10은 실제 앱(제품 코드)으로 확인했습니다. 검증 코드는 [Spikes/SeparatorSpike](../../Spikes/SeparatorSpike/). 설계는 [ADR-0012](../adr/0012-separator-visibility-macos26.md).

### 7.1 허용 목록 기능이 없다

- `/System/Library/PrivateFrameworks/MenuBarClientCore.framework`와 `MenuBarClient.framework`가 **없습니다** (`dlopen` 실패). `MBAssessmentModeConfiguration`, `MBAssessmentModeAssertion`, `MBMenuBarItemManager`, `VisibilityRestrictionAssertion` 클래스도 없습니다.
- `MenuBarAgent` 프로세스가 없습니다. 메뉴바 관련 프로세스는 `ControlCenter`와 `SystemUIServer`입니다.
- 그래서 1.0.2는 이 버전에서 "이 macOS 버전에서는 숨김을 쓸 수 없습니다"로 표시합니다. 판정은 정상입니다 (`MBKVisibilityBridge.isSupported`가 거짓).
- 이름이 비슷한 `AEAssessmentMode…` 클래스들(`AutomaticAssessmentConfiguration`, `AACCore`)은 시험 감독용 공개 기능의 일부로, 메뉴바 허용 목록과는 다른 것입니다.

### 7.2 창 구조

| 소유 프로세스 | 레이어 | 크기 | 비고 |
|---|---|---|---|
| `Window Server` | 24 | 2056×39 | 메뉴바 배경 (창 이름 `Menubar`) |
| `ControlCenter` | 25 | 아이콘마다 1개 (폭 31~176) | 서드파티 앱의 아이콘 창도 **모두 제어 센터 소유** |

- macOS 27과 달리 **아이콘마다 창이 있습니다.** 창 목록(`CGWindowListCopyWindowInfo`)으로 권한 없이 각 아이콘의 위치·폭을 읽을 수 있습니다.
- 다만 소유 프로세스가 전부 제어 센터라, **창 목록만으로는 어느 창이 어느 앱의 아이콘인지 알 수 없습니다.** 창 이름은 화면 기록 권한이 없으면 비어 있습니다.
- 일부 앱(Magnet)은 자기 프로세스에도 레이어 25 창을 하나 갖고 있지만 크기가 0이고 화면에 없습니다.
- 자기 상태 아이템의 `button.window.frame`은 실제 위치와 일치합니다 (창 목록의 값과 같음).

### 7.3 구분자 확장으로 숨기기

자기 상태 아이템 세 개(왼쪽부터 H · S · V)를 만들고 가운데 S의 길이를 바꿔 봤습니다. 다른 앱의 아이콘 12개는 V의 오른쪽에 있습니다.

| S의 길이 | H (S의 왼쪽) | V와 다른 아이콘 12개 | 판단 |
|---|---|---|---|
| 10000 | x=−3720, 화면 밖 | 그대로 | ✅ 숨김 성공 |
| 4000 | x=−2720, 화면 밖 | 그대로 | ✅ |
| 2056 (화면 폭) | x=−776, 화면 밖 | 그대로 | ✅ |
| 1100 · 900 | 좌표는 화면 안(x=180·380)이지만 시스템이 표시하지 않음 | 그대로 | 숨겨지긴 하나 경계 조건 |
| 500 | 표시되지 않음 | **V와 다른 아이콘 7개가 함께 사라짐** | ❌ 쓰면 안 됨 |

- 길이를 되돌리면 모두 원래 자리로 돌아옵니다 (1초 안).
- 길이 10000을 주면 실제 창 폭은 5016으로 잡힙니다.
- 구분자가 메뉴바에 들어가긴 하지만 다른 아이콘을 밀어낼 만큼만 긴 경우(500), 시스템이 자리가 모자란 아이콘들을 통째로 감춥니다. **길이는 항상 화면 폭보다 훨씬 크게** 줍니다.
- 미확인: 숨김 중 왼쪽의 앱 메뉴·빈 영역 클릭 (구분자 창이 x=0부터 덮고 있음. 시스템은 이 창을 "가려짐"으로 보고함).

### 7.4 복구

| 상황 | 결과 |
|---|---|
| 길이를 되돌림 | 즉시 복구 |
| 구분자를 펼친 채 `SIGKILL` | 0.3초 뒤에는 아직 그대로였고, 1초 뒤에는 원래의 12개만 남음 (전부 표시) |

프로세스가 끝나면 그 프로세스의 상태 아이템이 사라지므로, 별도 처리 없이 전부 표시로 돌아갑니다.

### 7.5 새 아이콘은 숨김 쪽에 놓인다

- 구분자를 펼친 동안 새 상태 아이템을 만들면 **구분자의 왼쪽(x=−3758, 화면 밖)** 에 놓입니다. 접으면 맨 왼쪽에 나타납니다.
- 즉 이 방식도 macOS 27의 허용 목록처럼 **기본이 "차단"** 입니다. 숨김 중에 새 메뉴바 앱이 실행되면, 그 아이콘을 구분자 오른쪽으로 옮겨 줘야 보입니다.
- **예전에 자리를 잡았던 앱은 다시 실행하면 그 자리에 바로 나타납니다** (숨김 중에도). 아이콘의 위치는 그 앱의 기본값에 `NSStatusItem Preferred Position <아이템 이름>`으로 저장되고, 값은 모니터 오른쪽 끝에서의 거리입니다. 이 값을 지우고 실행하면 처음 보는 아이콘처럼 숨김 쪽에 놓입니다.

### 7.6 접었을 때의 폭

- 길이를 0으로 줘도 실제 폭은 **16pt** 입니다. 구분자는 접은 상태에서도 16pt의 빈칸을 차지합니다 (제목·그림이 없으면 보이지는 않음).
- 길이 0에서 곧바로 10000으로 바꿔도 정상으로 숨겨집니다.

### 7.7 접근성으로 아이콘 읽기 — T1

제품 코드(`AXItemDiscovery`)를 고치지 않고 그대로 실행했습니다.

- **macOS 27과 같은 방법으로 읽힙니다.** 각 앱의 `AXExtrasMenuBar` 자식에서 위치·크기를 얻었고, 화면에 보이는 15개가 모두 소유 앱과 함께 나왔습니다 (서드파티 6개 앱, 검증용 아이콘 3개, 입력 소스, Siri, 제어 센터의 4개).
- 아이콘 창은 제어 센터 소유(7.2)지만, **좌표로 요소를 찾으면(`AXUIElementCopyElementAtPosition`) 원래 앱의 `AXMenuBarItem`이 나옵니다.** 그래서 "그 좌표에 실제로 있는지" 확인(3.21)이 그대로 통합니다.
- 걸린 시간: 실행 중인 모든 앱을 훑는 전체 조회 0.82초, 아이콘이 있던 프로세스만 보는 다시 조회 0.07~0.10초.
- **시스템 아이콘에 이름과 식별자가 있습니다** (macOS 27에서는 비어 있음 — 3.21). 제어 센터 프로세스: 배터리 `com.apple.menuextra.battery`, 시계 `com.apple.menuextra.clock`, Wi-Fi `com.apple.menuextra.wifi`, 제어 센터 `com.apple.menuextra.controlcenter`. Siri는 `SystemUIServer`, 입력 소스는 `TextInputMenuAgent` 프로세스에 있습니다.
- 제어 센터의 `AXExtrasMenuBar`에는 자식이 15개인데, 위 4개를 뺀 11개는 크기 0에 좌표 (0, 1329)인 빈 항목입니다. 폭이 0이라 지금 코드에서 걸러집니다.

### 7.8 화면 밖으로 밀린 아이콘의 좌표 — T3

- 구분자를 펼친 상태에서 읽으면, 숨겨진 아이콘은 **실제 화면 밖 좌표**로 나옵니다 (예: x=−3691). macOS 27처럼 예전 좌표를 돌려주지 않습니다.
- 그 좌표에는 요소가 없으므로(조회 실패 −25200) "지금 표시된 아이템" 목록에서는 빠집니다. 펼친 상태 15개 → 숨긴 상태 12개.
- 따라서 **펼치지 않고도 어느 아이콘이 숨김 쪽에 있는지 알 수 있습니다** (x가 구분자보다 왼쪽인지).
- 숨김 중에 메뉴바 왼쪽(x=300, 700)과 구분자가 덮고 있는 빈 영역(x=1311)의 요소를 찾으면 앞에 있는 앱의 메뉴바가 나옵니다. 구분자가 앱 메뉴를 가로막지 않는 것으로 보이지만, 실제 클릭은 해 보지 않았습니다.

### 7.9 ⌘+드래그 합성으로 구분자 넘기기 — T2

제품 코드(`EventSynthesisReorderer`)를 그대로, 속도도 기본값(6pt마다 한 걸음, 12ms 간격, 놓기 전 250ms)으로 실행했습니다.

| 옮긴 것 | 결과 |
|---|---|
| 검증용 아이콘 V를 구분자 S의 왼쪽으로 (H·S·V → H·V·S) | ✅ 한 번에 들어감. 펼치면 V도 화면 밖으로 밀려남 |
| V를 다시 S의 오른쪽으로 | ✅ |
| **다른 프로세스의 아이콘**(MenuBarManager)을 S의 왼쪽으로 | ✅ 펼치면 숨겨짐 (x=−3691). 그 앱은 실행 중인 채로 아무 영향 없음 |
| 그 아이콘을 원래 자리로 | ✅ 검증 뒤 12개 아이콘의 위치가 시작할 때와 같음 |

- 놓는 지점은 macOS 27과 같습니다: **목표 아이콘의 왼쪽 가장자리에서 6pt 왼쪽**에 놓으면 그 아이콘 바로 앞에 들어갑니다. 왼쪽·오른쪽 이동 모두.
- 한 번 옮기는 데 약 1.3초 걸립니다.
- 미확인: 폭이 넓은 아이콘, 시스템 아이콘을 옮기는 것.

### 7.10 실제 앱(MenuBarManager)에서 확인한 것

제품 코드의 Debug 빌드를 `/Applications`에 설치하고, 설정 사본(`-stateDir`)으로 실행해 명령 채널로 확인했습니다. 숨길 대상은 검증용 앱(SeparatorSpike)의 아이콘 세 개로 해서 사용 중인 다른 앱의 순서는 건드리지 않았습니다.

| 확인한 것 | 결과 |
|---|---|
| 권한 없이 시작 | "접근성 권한 필요" 상태로 시작, 구분자는 폭 16pt로 메뉴바 가장 왼쪽에 만들어짐 |
| 권한을 켠 뒤 | 앱이 2초 안에 알아채 "숨기기 꺼짐"으로 넘어감 |
| 숨기기 켜기 | 아이콘 3개를 구분자 왼쪽으로 옮기고 숨김. 명령부터 숨김 상태까지 4.6초. 다른 아이콘 12개는 그대로 |
| 펼치기 / 다시 숨기기 | 4ms / 0.43초 (구분자는 바로 늘어나고, 배치를 확인한 뒤 상태가 바뀜) |
| 숨김 중에 "표시"로 바꿈 | 잠깐 펼쳐 3개를 구분자 오른쪽으로 옮기고 다시 숨김 |
| 숨김 중에 처음 보는 앱이 실행됨 | 숨김 쪽에 놓인 아이콘 3개를 표시 쪽으로 옮김 (16초 뒤에 확인했을 때 끝나 있었음. 정확한 시간은 재지 않음) |
| 순서 읽기 | 잠깐 펼쳤다가 1.2초 뒤 다시 숨김. 숨긴 아이콘까지 읽힘 |
| 숨김 중 `SIGKILL` | 2초 안에 전부 표시 |
| 앱을 다시 실행 | 구분자가 같은 자리(자기 아이콘 바로 왼쪽)에 놓임. 이 앱의 기본값에 `MenuBarManagerSeparator` 695, `MenuBarManagerMain` 659로 저장되어 있음 |

- **내용이 없는 구분자는 접근성 목록에 나오지 않습니다.** 접혀 있을 때(폭 16pt) `AXExtrasMenuBar`의 표시된 아이템에 구분자가 없었습니다. 그래서 순서 목록에서 따로 뺄 것이 없습니다.
- **여러 아이콘을 옮기면 순서가 뒤집혔습니다.** 옮긴 아이콘은 구분자 바로 옆에 놓이기 때문에, 왼쪽 것부터 차례로 표시 쪽으로 옮기니 H·S·V가 V·S·H가 됐습니다. 표시할 것은 오른쪽 것부터 옮기도록 고쳤고, 고친 뒤에는 단위 테스트로만 확인했습니다 (실제 메뉴바에서는 미확인).
- **접근성 권한 항목(3.20)은 이 버전에서도 빌드에 묶입니다.** 임시 서명한 새 빌드로 바꾼 뒤 손쉬운 사용 목록에서 스위치를 껐다 켜는 것으로는 권한이 적용되지 않았고(두 번 시도), 항목을 지우고 새로 추가해 켜자 적용됐습니다. 권한 항목이 없던 검증용 앱은 요청 창 → 켜기만으로 적용됐습니다.

### 7.11 아직 모르는 것
