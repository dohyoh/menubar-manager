# ADR-0005: OS 접점 격리와 비공개 API 사용 원칙

- 상태: ✅ 채택
- 날짜: 2026-11-10
- 관련: [architecture/overview.md](../architecture/overview.md) · [ADR-0003](0003-visibility-mechanism.md) · [ADR-0004](0004-reorder-mechanism.md)

## 맥락

메뉴바 관리에는 공개 API가 없어, 어떤 방식을 택하든 문서화되지 않은 시스템 동작에 기댑니다. macOS 26과 27에서 연달아 메뉴바 구조가 바뀌어 기존 관리 앱들이 두 번 깨졌습니다. 같은 일이 다시 일어난다고 가정하고 설계해야 합니다. 또한 메뉴바는 시스템 핵심 UI라, 이 앱의 오류가 사용자의 아이콘을 사라지게 해서는 안 됩니다.

## 결정

1. **프로토콜 뒤에 숨깁니다.** OS에 닿는 기능(열거, 숨김, 순서 변경, 권한, 호환성 검사)은 `MenuBarDomain`에 프로토콜로 정의하고, 구현은 `MenuBarSystem` 모듈에만 둡니다. 나머지 모듈은 `MenuBarSystem`을 import하지 않습니다.
2. **비공개 API는 한 파일군에.** 비공개 클래스명·셀렉터 문자열은 `MenuBarPrivateBridge`(Objective-C) 밖에 두지 않습니다. 링크하지 않고 런타임 조회(`dlopen`, `NSClassFromString`, `respondsToSelector:`)로만 접근합니다.
3. **없으면 조용히 물러납니다.** 클래스·메서드가 없거나 호출이 실패하면 크래시 없이 "지원 안 됨"을 반환합니다. 앱은 실행 시 자가진단을 돌려 기능별 사용 가능 여부를 판단합니다 (FR-8).
4. **Fail-open.** 오류·비호환·종료 시 항상 "전부 표시"로 되돌립니다 (FR-5).
5. **조사 결과는 문서로.** OS 동작에 대한 사실은 [platform-notes.md](../architecture/platform-notes.md)에 검증 여부와 함께 기록하고, 관련 코드에서 링크합니다.

## 검토한 대안

| 대안 | 판단 |
|---|---|
| 비공개 API를 쓰지 않는다 | macOS 27에서 FR-1을 충족할 공개 수단이 없음 → 기각 |
| 추상화 없이 직접 호출 | 빠르지만 OS가 바뀔 때 전체를 고쳐야 하고 테스트 불가 → 기각 |
| 비공개 프레임워크를 직접 링크·헤더 선언 | 심벌이 사라지면 실행 시 즉시 크래시 → 기각 |

## 결과

- OS가 바뀌면 `MenuBarSystem`의 구현체만 교체·추가하면 됩니다.
- Domain·Services는 가짜 백엔드로 자동 테스트할 수 있습니다.
- 프로토콜 계층만큼 코드가 늘어납니다 — 감수합니다.
- macOS 메이저 업데이트마다 M0의 검증 질문을 다시 돌리는 것이 유지보수 절차가 됩니다.
